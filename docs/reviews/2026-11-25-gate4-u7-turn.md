## Findings

**G1 (Medium): a tool's 5-second limit does not bound its transaction.** `packages/db/src/outbound.ts:436` (`runTool`).
- `Promise.race` rejects at the timeout, but the tool's query is still in flight on the same connection, so the `ROLLBACK` queues behind it.
- Probe: a tool running `SELECT pg_sleep(3)` with `timeoutMs: 100` returned `failed` after 3,010 ms.
- The conversation row stays locked (`FOR NO KEY UPDATE` in `holdsLease`) for that whole time. The real bound is 5 s plus one statement at `statement_timeout` 4 s, about 9 s, and inbound storing has `lock_timeout` 3 s.
- The note's L3 ("the 5 seconds matter because…"), its S2b sum, and the architecture's "with a limit of 5 seconds" are wrong. Sixteen such tools give 100 + 25 + 144 = 269 s, over the 240 s handler limit (`JOB_HANDLER_TIMEOUT_MS`).
- Fix: set `SET LOCAL statement_timeout` to the time remaining, or cancel the in-flight query at the deadline, and correct S2b.

**G2 (Medium): the lease-renewal test is tautological and two lease branches are untested.**
- `apps/worker/src/turn.test.ts:788` (L7) passes one fixed `later` to every renewal, so a second renewal is indistinguishable from none. Mutant 4 (renew only when `round === 0`) survives.
- Mutant 8 (ignore `lost-lease` from `runTool`, `turn.ts:251`) survives: the next `renewTurn` hides it.
- Mutant 32 (drop the lease check in `runTool`'s second transaction, `outbound.ts:464`) survives. A `failed` row can be written for a conversation another worker now holds, and nothing tests it.
- Fix: advance the clock between calls in L7, assert the outcome and call count in L4, and add a test that loses the lease between the two transactions.

**G3 (Medium): `sessionHistory` has no index to use.** `outbound.ts:343`.
- It filters on `session_id` alone. The `messages` indexes are `(tenant_id, conversation_id, …)` partials, `(tenant_id, id)` and `(tenant_id, answered_by)`; none holds `session_id`.
- `EXPLAIN` shows `Seq Scan on messages` plus a sort (on a tiny test table, but no usable index exists either way).
- Every turn reads the tenant's messages. The note's section 10 and the migration say nothing about it.
- Fix: add `messages (tenant_id, session_id, created_at, id)` in 0010, or filter by `conversation_id` too.

**G4 (Low): the history's text bound stops at the first message that does not fit, and is untested either way.** `outbound.ts:356`.
- `break` is right for a contiguous history, but mutant 29 (`continue`, which leaves a hole) survives.
- One newest message over 12,000 characters empties the whole history. The H5 test asserts this, but the note's "the newest that fit both" does not say it.
- Mutant 30 (drop `kind = 'text'`) also survives: H4 has no test with a non-text row that holds a body.

**G5 (Low): the stand-in does not always make a reply the client accepts, contrary to A3.** `packages/ai/src/standin.ts:37`, against `output.ts:35`.
- Probe through `bounded(standInEcho())`: customer text `a\tb`, `a\r\nb` and `a\u0085b` each give `invalid-output shape`. Plain text, 1,100 emoji and bidi controls are fine.
- In development and e2e, a pasted tab or CRLF means the turn ends `model-invalid-output` and the customer silently gets nothing.
- Fix: replace `\p{Cc}` other than `\n` in the stand-in, or correct A3.

**G6 (Low): the sent copy can differ from what the answer is checked against.** `bounded.ts:259-260` against `516-517`.
- `markedCopy` reads `request.tools`, `request.claimKinds` and `request.system` again after `offered` was captured.
- Probe: a `claimKinds` getter returning `["price"]` on its first two reads and `["evil"]` afterwards made the adapter receive `["evil"]` while the answer was checked against `["price"]`.
- `tools` are copied one level deep (`{ ...tool }`), so `argumentsSchema` stays shared with the caller during the call.
- `structuredClone(toolCalls)` at line 218 is untested: mutant 20 (aliasing) survives.
- Reachable only from this repository's own callers, but the comment "what was checked is what is used" is not true for these fields. Fix: build the copy from the values already read, and deep-copy tools.

**G7 (Low): `runTool` throws when `arguments` cannot be stored as `jsonb`.** `outbound.ts:409` and `467`.
- Probe: `{ q: "a\u0000b" }` and a key holding U+0000 both throw `unsupported Unicode escape sequence`, because the `failed` insert fails for the same reason.
- In `runTurn` that would fail the job, and each of the six tries calls the model again.
- Not reachable through the client today: `readOutput` refuses control characters in argument texts and keys. The only guard is in another package.
- Fix: store `arguments` as null when the insert of the `failed` row is refused.

**G8 (Low): untested branches in `turn.ts`.**
- Line 199: a pack with a fragment that was not loaded should give `unknown-pack`. Mutant 10 survives.
- Line 214: `turnStartedAt`. Mutant 12 (`new Date(0)`) survives.
- The note's section 8 says the time is "read when `beginTurn` returns". The code reads the worker's clock after five database round trips.

**G9 (Note): where the note and the code disagree.**
- **S4** says an empty reply is "already refused by the client". The code has its own `empty-reply` exit (`turn.ts:231`) for a reply of only spaces, which the client accepts; the test covers it, the note does not.
- **S2a** says the batch is marked. If a newer message arrived, `finishTurn` with no reply returns `newer-message` and marks nothing. The batch is answered again with the next message, so the model is called again for an answer "not tried again". This follows from the `finishTurn` code; I did not run it.
- **M7** does not mention `toolCallId`. It is model-written, sent unmarked on `tool-result` messages, and bounded only by `TOOL_CALL_ID_MAX`.
- **Section 11** lists the glossary for the two history numbers. `docs/requirements/glossary.md` is not in the diff, and "12,000" appears in no document outside the note.
- **Prompt rule 7** says 1,000 characters; the client's limit is 1,200. This is a margin rather than an error, but no document says it is deliberate.
- No document I read claims an eval exists. The note, `meta.yaml`, the CHANGELOG, the prompts README and STATUS all say none has run.

## What I could not fault

- **What reaches the model.** `buildRequest` and `businessData` have no contact parameter. History is scoped by session under RLS, limited to `assistant-reply` rows with the right statuses, and tests H2a and H6 kill the mutants.
- **Marking.** Every text role is wrapped, messages are read once, extra fields are dropped, the adapter receives only the marked copy, and the trace carries no text. The stand-in's unmarking strips only the outer mark.
- **`runTurn` exits.** No double release, no release of a lease that was lost, `abandonTurn` on every throw. The loop makes five calls with four tool rounds, as the note says.
- **Production refusal.** The stand-in is refused independently of the shared credential, and the example canary is caught as a placeholder (probe returned both reasons).
- **Tool results.** A lying `toJSON` is stored and returned identically; a lone surrogate, an over-long result and a throwing tool all end `failed`. No unhandled rejection after a timeout.
- **Migration 0010.** The constraints, grants and FORCE RLS are all tested; the down migration drops in a valid order.
- **Image.** `prompts/` and `tools/demo-profile.json` are not excluded by `.dockerignore`, and `main.ts` resolves `prompts/` from the repository root (by reading, not by building).
- **Prompt.** It holds the eight points of section 9, and the order it describes matches `buildRequest`.
