# Review of ADR 0014 (M3 U1), branch `docs/300-m3-u1-pack-interface`

Reviewed in a copy at `/tmp/u1review`, commit `ca6ce86` over `main` (`eb9a3b2`). Paths are relative to the repository; "ADR" alone means `docs/adr/0014-pack-interface.md`.

## Verdict

The ADR settles the registration mechanism (one typed object per pack, a static registry, three packages) and that is buildable. It does not settle the parts well enough for the units to build without asking again. The button payload's "reference" is undefined and contradicts the data model. "The tenant's database scope" contradicts ADR 0003's amendment, which nothing mentions. The step rewrites drop step 15 and several behaviours of steps 6, 10 and 13. The Button part has no label and no "handled by code" marker, although both are relied on. The package that actually consumes a pack's tools and claim kinds (`ai`) is never named, and "the core" is used for both `packages/core` and "everything that is not a pack". The `faq-only` removal breaks more than `ops`: six test fixtures and two documented enums use the name, and the ADR's "refused job" rule makes those fixtures fail. The plan's unit order and scopes were not updated, so STATUS's "Next" schedules U5 before the unit the ADR says creates the packages U5 needs. The session outcome, which the plan's U1 scope names, is deferred without saying the plan asked for it. I would not merge it as is: D1 to D6 need a decision in the record, and D7 and D8 need a row for the maintainer.
